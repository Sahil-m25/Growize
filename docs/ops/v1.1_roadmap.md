## 1. WhatsApp RM button on Support screen

**Owner:** TBD
**Size:** 1–2 hours
**Priority:** P1 (launch-adjacent — high investor preference signal)

### Problem
HNI investors do not use ticket forms. They want to ping their Relationship Manager (RM) over WhatsApp the same way they do for every other private banking / wealth product they hold. The current Support screen offers only a "Create Ticket" form, which is a friction point for a cohort that values immediacy and a personal touchline.

### Change
Replace (or supplement) the primary CTA on the Support screen with a WhatsApp deep-link button. Tapping it opens WhatsApp (mobile) or wa.me (web) with a prefilled message to the assigned RM.

- v1.1 implementation: hard-code the RM phone number in `lib/env/env.dart` (e.g., `arlRmWhatsappNumber`). One RM for all investors during the private launch.
- Prefill: `"Hi, this is <investor.name> (ARL ID <investor.arl_id>). I need help with: "`
- Format: `https://wa.me/<RM_PHONE>?text=<encoded_message>`
- Keep the ticket form behind a "Or raise a ticket" secondary link so the existing audit trail still works.

### v1.2 follow-up (out of scope here)
Make the RM number data-driven (`investors.assigned_rm_phone`). Add per-RM round-robin if we onboard 2+ RMs.

### Acceptance
- Support screen primary CTA is "Chat with your RM on WhatsApp".
- Tapping it opens WhatsApp with the prefilled text on both web and Android.
- Ticket form still reachable from a secondary link.
- Env variable change documented in `docs/ops/ops_admin_guide.md`.

## 2. Share-project button (Explore) + post-payout referral nudge

**Owner:** TBD
**Size:** 2–3 days
**Priority:** P1 (free growth loop — fills the next project without ad spend)

### Problem
We expect strong word-of-mouth for the first 50 investors. Today there is no in-app primitive to share a specific project (in Explore) or to invite a friend after a positive moment (a payout). Every share happens via screenshot + WhatsApp, which we cannot attribute.

### Change

**Part A — Explore: per-project share button**
- Add a share icon on each marketplace project tile and in the project detail card.
- Tapping it calls a new Supabase Edge Function `mint-share-token` that creates a row in `share_tokens` (`token`, `project_id`, `referrer_investor_id`, `created_at`, `expires_at`, `clicked_count`).
- The function returns a short URL `https://app.growize.in/p/<token>` (or `growize://p/<token>` in mobile builds).
- The native share sheet opens with a templated message: `"<Investor name> thinks you'll like this farm: <project name> in <location>. <short_url>"`.

**Part B — Deep-link routing**
- On open, the app reads the token, calls Supabase to resolve the project, increments `clicked_count`, and lands the user on the project detail. If unauthenticated, they go through the existing magic-link flow first; the token persists across auth.
- Attribution: when a referred user later becomes an investor, set `investors.referred_by = referrer_investor_id` for the first 30 days after first click.

**Part C — Post-payout nudge**
- When a payout lands (Activity feed entry), the home tab shows a one-time bottom-sheet: "₹X just hit your account. Like ARL? Send a friend." with two buttons: "Share Growize" (opens the project share flow scoped to "any project") and "Maybe later".

### Schema
```sql
CREATE TABLE share_tokens (
  token text PRIMARY KEY,
  project_id uuid REFERENCES projects(id),
  referrer_investor_id uuid REFERENCES investors(id),
  created_at timestamptz DEFAULT now(),
  expires_at timestamptz DEFAULT now() + interval '30 days',
  clicked_count int DEFAULT 0
);
ALTER TABLE investors ADD COLUMN referred_by uuid REFERENCES investors(id);
```

### Acceptance
- Share icon visible on every Explore tile and project detail.
- New tokens land in `share_tokens` with correct FK to investor.
- A clicked link from a logged-out browser resolves to the right project after auth.
- `investors.referred_by` is set on first sign-up via a shared link.

## 3. First-payout celebration moment

**Owner:** TBD
**Size:** 1–2 days
**Priority:** P0 (highest-intent moment in the investor lifecycle — once-per-investor opportunity)

### Problem
The first payout is the most emotionally significant moment in the entire investor journey. Right now it shows up as a row in the Activity feed identical to every subsequent payout. We are leaving the strongest possible referral/social-proof signal on the table.

### Change
- Add `investors.first_payout_seen boolean DEFAULT false`.
- When the home tab loads, query: any `payouts` rows for this investor where `paid_at IS NOT NULL`? AND `first_payout_seen = false` → trigger a full-screen modal.
- Modal copy: **"Your first payout has arrived"** with the amount large and animated (Lottie or simple scale-in), the project name, and two CTAs:
  - Primary: "Share this with a friend" → opens the v1.1#2 share-flow scoped to that project, with prefilled text `"My first payout from <project> just landed: ₹<amount>."`
  - Secondary: "Continue to dashboard"
- On dismiss, set `first_payout_seen = true`. Never show again.

### Schema
```sql
ALTER TABLE investors ADD COLUMN first_payout_seen boolean DEFAULT false;
```

### Acceptance
- Investor with no prior payouts receives a payout → on next home load, modal appears.
- Modal can be dismissed; the flag is set; the modal does not re-appear on subsequent sessions.
- Sharing CTA flows into the v1.1#2 share infra.

## Post-v33 (queued — not in v1.0 scope)

Added 2026-05-20. These items came up during the v33 design refresh but were intentionally deferred so v1.0 could ship for the private email launch. None of them block v1.0; all of them are bounded and should slot cleanly into a v1.1 follow-on cycle.

### 1. In-app "new version available" banner

**Why.** Today we have no in-app update prompt. Investors on stale APKs silently miss server-side feature gates and migration-driven UI changes. After v33 widened the `notifications.type` enum we saw stale APKs on old builds render an empty notification card for `phase_update` events because their client didn't recognize the type.

**Shape.**
- New table: `app_releases` (`platform`, `min_supported_build`, `latest_build`, `is_force_update`, `release_notes`, `published_at`).
- New edge function: `get-latest-release` (no auth, GETs the row for the requesting platform). Cached at the CDN edge — version checks are cheap.
- Flutter app calls `get-latest-release` on cold start. If `currentBuild < min_supported_build`, show a blocking modal ("Update required"); if `currentBuild < latest_build`, show a dismissible banner ("Update available — what's new").
- Supabase-only (no Play Store / App Store dependency). The APK link in the banner points to the same email-attached APK URL we use today.

**Acceptance.**
- Stale build sees the banner on the next cold start within 30s of `app_releases.latest_build` being incremented.
- Banner dismissal persists until next launch.
- Force-update mode blocks all routes except the banner CTA.

### 2. Real hero photos

**Why.** Six P2 audit defects all share the same root cause: Project Detail, Projects List, Explore tiles, Explore Detail, Project View Area, and the Share-modal preview card all use Unsplash placeholders or gradient color tiles with letter overlays. The marketplace is at the point where each LLP has a real on-site photo we should be surfacing.

**Shape.**
- New Supabase storage bucket: `project-heroes` (public read, ops-only write).
- New columns: `projects.hero_image_path` (text), `projects.hero_blurhash` (text, 32 chars) for placeholder-while-loading.
- Bulk-upload Day-1 hero per LLP via the existing ops admin tool. Once `hero_image_path` is non-null for an LLP, the Flutter app prefers it over the Unsplash placeholder.
- Falls back to the existing gradient tile if both Supabase and Unsplash fail.

**Acceptance.**
- All LLPs in production have a non-null `hero_image_path`.
- Cold-load shows blurhash placeholder; full image fades in within ~400ms on a typical 4G connection.
- Removes audit P2 defects #8, #11, and #16 in one stroke.

### 3. WhatsApp Business API integration

**Why.** v33 added WhatsApp Tech + WhatsApp RM CTAs to the Support screen, but they're link-outs (`wa.me/<phone>?text=<prefilled>`). The hybrid-ticket trick gives us an audit trail of who clicked, but we have no signal on whether ops actually replied, and replies don't flow back into the app. Investors who never reopen the support form never see the response.

**Shape.**
- Move to WhatsApp Business API (Meta Cloud API tier).
- New edge function: `whatsapp-webhook` (verified by Meta) receives inbound messages → routes to the matching `support_tickets` row by phone number → posts as a `ticket_replies` row with `channel='whatsapp'`.
- Outbound from the Support screen still uses `wa.me` deep-links for v1.1, but the inbound side closes the loop.
- v1.2 (or v1.1 stretch): outbound from the app too — investor types in the Support form, message is posted to WhatsApp Business via the Cloud API instead of opening the wa.me link.

**Acceptance.**
- Ops replies on WhatsApp Business → message appears in the in-app ticket thread within 10s.
- Read receipts visible on both sides.
- All inbound/outbound messages logged in `ticket_replies` with `channel='whatsapp'` for audit.

### 4. iOS bundle

**Why.** Still blocked on Apple Developer enrollment (paperwork stage, not technical). When unblocked, the Flutter codebase already builds for iOS — we just need a signing cert + provisioning profile + App Store Connect listing.

**Shape.**
- Enroll Apple Developer Program (org account, not personal — needs DUNS).
- Generate distribution cert + provisioning profile. Wire them into `ios/Runner.xcodeproj` and `flutter build ipa`.
- TestFlight build for the same private email list that today gets the APK.
- App Store Connect listing for the eventual public launch (separate scope — v1.2 minimum).

**Acceptance.**
- TestFlight build installable on enrolled devices.
- All v1.0 features work on iOS (no platform-specific Flutter regressions). View Area "Open in Maps" deep link correctly hits `maps://` instead of `geo:` on iOS.
- Push notifications work via APNs (separate v1.2 track; the iOS bundle just lays the groundwork).
