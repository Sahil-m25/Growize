## Agent B — Prompt-injection / XSS

### B-1. P1 — `app_releases.apk_url` / `web_url` accepted with no allow-list, then handed to `launchUrl()`
- **Location:** `lib/core/version/version_banner.dart:36-46`, `lib/core/version/app_version_check.dart:111-117`, `supabase/functions/latest-app-version/index.ts:65-91`
- **Issue:** The "new version available" banner pulls `apk_url` / `web_url` from the `app_releases` row (read via service-role in `latest-app-version` edge fn), and `_openUpdateUrl` does `Uri.tryParse(raw) → launchUrl(uri, mode: LaunchMode.externalApplication)` with **no scheme/host allow-list and no domain check**. Any actor who can write a row to `app_releases` (and the table has no RLS visible in any of the migrations under `supabase/migrations/` or `supabase/migrations_archive_20260608/` — the only writer is the studio/admin path) can replace the legitimate `https://*.google.com/...` update URL with `https://attacker.example/malware.apk` or a phishing page. Worse, the critical-update path (`update.isCritical`, `version_banner.dart:91-93`) shows a non-dismissible `AlertDialog` with an "Update now" button that fires the same launch — so a single bad row can force every user to a malicious URL on next app launch.
- **Impact:** Open redirect / force-navigation to attacker-controlled URL, scoped to the user population. Combined with the fact that a `https://` APK URL is offered, this is a drive-by malware vector (the OS browser will not prompt before download). Phishing is trivial — a `https://attacker.example/login` URL that mimics Growize will harvest Supabase OTPs (which are accepted by the legitimate `request-auth-email` flow once an email is entered).
- **Fix:** (a) Reject any URL whose host is not in a static allow-list (`play.google.com`, `apps.apple.com`, `arl.app` / `agresearchlabs.com`); (b) For `isCritical=true`, never auto-launch — require an explicit user tap *and* render the destination host on the dialog button (e.g. "Update via Play Store") so the user can sanity-check. (c) In the SQL schema for `app_releases`, add a CHECK constraint or a trigger that validates the URL pattern, and add RLS so only the `service_role` can write it (read-only for everyone else).

### B-2. P1 — `.env` bundled verbatim into release APK (and web build)
- **Location:** `pubspec.yaml:96-97` (`assets: - .env`), confirmed present at `build/app/intermediates/flutter/release/flutter_assets/.env` (1041 bytes, identical mtime to source). Conflict with `lib/main.dart:70-82` which says "Load dotenv on native only" — the asset declaration contradicts the runtime load guard and ships the file regardless.
- **Issue:** Per the comment in `lib/core/constants/supabase_constants.dart:5-11`, the `.env` is the runtime fallback for `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SENTRY_DSN`. The anon key is a JWT — publishing it in a client asset is expected for Supabase apps, but bundling the **whole `.env` file** in `flutter_assets/` (vs only the keys) means: (i) any additional secrets anyone adds to `.env` (Zoho credentials, future SMS provider keys, dev bypass flags) get shipped to every user, (ii) the file is `unzip`-extractable from any APK in 5 seconds. The `.env.example` comment at line 16-18 explicitly warns *"Read at COMPILE TIME via `flutter build ... --dart-define-from-file=.env.production`, NOT bundled as a runtime asset"* — so the asset declaration is contradicting the documented design.
- **Impact:** Any future secret placed in `.env` leaks. Even today, the file shape reveals the Supabase project ID `oynfhdqizebvgmaoiuax` (in the example) and any other values present. Risk is bounded by current `.env` contents, but the pattern is a foot-gun for the next dev who adds a key.
- **Fix:** Remove `- .env` from `pubspec.yaml`. For local dev with the bundled-file fallback, use `--dart-define` (already supported by `SupabaseConstants._envOr`) or a `kReleaseMode`-only branch that refuses to fall back to the asset. For production web, the `flutter build web --dart-define-from-file=.env.production` path is already documented and must be the only one used.

### B-3. P2 — `notify-consultation-request` posts user message to Slack as raw `mrkdwn` (no escaping)
- **Location:** `supabase/functions/notify-consultation-request/index.ts:132-156`
- **Issue:** `const msg = (consultation.message ?? "").trim();` is interpolated directly into a Slack `mrkdwn` block: `text: \`*Message:*\n${msg}\``. Slack mrkdwn is not HTML — `<script>` is rendered as literal text, and the only "executable" tokens are `@user`, `<!channel>`, `*bold*`, `_italic_`, links via `<url|label>`. An attacker who can post a `consultation_requests` row can inject `<!channel>` to spam the whole Slack workspace, or include a `mailto:`/phishing link wrapped in `<url|...>` to social-engineer the on-call team. Names (`investorName`, `investorEmail`, `investorPhone`) and project fields are also unescaped — same mrkdwn-injection surface.
- **Impact:** Slack workspace spam, phishing, and social-engineering pivot to the ops team. Not RCE, not data exfil from the app, but reputational and a real risk if ops uses the same channel for alerting.
- **Fix:** Replace `*`, `_`, `<`, `>`, `[`, `]` in user fields with their mrkdwn escape sequences (or use Slack's `plain_text` block type, which has no formatting at all), and validate `consultation.message` server-side to a reasonable length cap (e.g. 2000 chars) before send. The Sentry DSN is fine here since it's server-side env.

### B-4. P2 — Web CSP allows `'unsafe-eval'` (mitigated by Flutter web, still a misconfiguration)
- **Location:** `netlify.toml:33` — `script-src 'self' 'unsafe-inline' 'unsafe-eval'`
- **Issue:** The deploy CSP whitelists `'unsafe-eval'`. Flutter web's canvas-kit renderer needs this on first load, but `'unsafe-eval'` is the single most permissive directive in the CSP and means any future inline script in `web/index.html` (or any compromise of the Flutter build pipeline) can `eval()` arbitrary JS in the same origin. `'unsafe-inline'` on `script-src` is also enabled, but at least Flutter web's hashed bootloader can't work without it. `connect-src` is correctly narrowed to `*.supabase.co` + Sentry EU ingest.
- **Impact:** If a future commit adds a third-party script tag to `web/index.html` (e.g. for analytics), or if a content-injection bug in any future feature lets a user payload reach `eval()`, the impact is full XSS in the web build's origin. Currently the only inline script in `web/index.html` is the splash-hide helper (lines 117-137), which is harmless and source-controlled.
- **Fix:** Switch to Flutter's `html` renderer or, if staying on `canvaskit`, use the `_canvasKitForceCpuOnly` workaround and drop `'unsafe-eval'`. If that's not feasible in the short term, at least move the splash-hide helper to a separate `.js` file referenced by `<script src="splash.js" defer></script>` so `'unsafe-inline'` on `script-src` can be removed.

### B-5. P3 — Syncfusion `SfPdfViewer.network` renders arbitrary PDFs with JS actions enabled (out-of-the-box default)
- **Location:** `lib/features/documents/document_viewer_screen.dart:359-373` — `SfPdfViewer.network(_url, enableTextSelection: false, ...)`
- **Issue:** Syncfusion's Flutter PDF viewer is built on PDFium (C++) and **does execute PDF JavaScript actions by default** (the `enableJavaScript` option exists and is `true` unless explicitly set false — and even then, JS-in-Forms and JS-in-Annotations run regardless). The viewer is fed URLs from `documents.signedUrl` — those URLs are signed Supabase storage links, so an attacker who can write a document row to the `documents` table (and has upload access to the `arl-documents` bucket) can serve a malicious PDF with embedded JS that fires on open. The blast radius is the in-app JS sandbox, but PDFium has had multiple memory-corruption CVEs (CVE-2023-38560 et al.) and on Android the viewer is running native code.
- **Impact:** Memory corruption / potential RCE in the native PDFium code path. Currently mitigated by the fact that documents are uploaded by staff, not by investors, but if investor-side uploads are added later this becomes a direct attack vector. The screen protection (FLAG_SECURE) reduces screenshot exfil risk but doesn't address the underlying native exploit.
- **Fix:** Set `enableJavaScript: false` on the `SfPdfViewer` constructor (if available in this version — verify the `SfPdfViewer.network` parameter list in the pinned `^27.1.48`). Add a per-document content-type / MIME check in `documentsRepository` to refuse `.pdf` documents whose `Content-Length` is unreasonable or whose PDF header doesn't start with `%PDF-`. For web build, document the `pdfx` fallback (already in `pubspec.lock`) and consider switching the mobile viewer to `flutter_pdfview` (no JS execution, MIT-licensed) for documents that came from external sources.

### B-6. P3 — `Growize App Design v2 (proposed).html` ships 38 `innerHTML` writes that interpolate script-controlled data (not deployed, but a foot-gun)
- **Location:** `Growize App Design v2 (proposed).html:2369, 2371, 2666, 2673, 2674, 2684, 2690, 2724, 2906, 2928, 3022, 3195-3232`
- **Issue:** This 367 KB design file uses `el.innerHTML = d.nextPayoutProject + '...'` style assignments 38 times, including user-content-style fields (`d.nextPayoutProject`, `d.nextPayoutRelative`). The file is **not in the Netlify deploy path** (`publish = "build/web"` per `netlify.toml:5`), so it's not live, but the comment at `CLAUDE.md:14` calls it the "single-file HTML/Tailwind prototype" that the Flutter app "must match pixel/behavior parity" with — meaning it could be shared with designers / stakeholders / opened from a shared drive, where it would be XSS-vulnerable if any of the demo data sources ever got fed untrusted content (the file currently has a `// HTML-escape helper` reference in `graphify-out/graph.html:60` but the v2 file itself does not escape). Lines 3200, 3205-3206 also build `iconWrap.innerHTML` from `TOUR_STEPS[i].icon` / `bullets` — fine for the current static data, but a broken `lucide` icon name is a vector if a designer ever wires this to a CMS.
- **Impact:** Zero in production (file not deployed). Latent XSS risk if the prototype is ever published on a public URL, sent to a contractor's environment with seeded data, or split into a CMS-driven version. The Flutter app mirrors the **layout**, not the data-binding — it uses `Text()` for everything, which is safe — so the production app is not exposed to this.
- **Fix:** Either (a) refactor the prototype to use `textContent` / `setAttribute` for the data interpolations and reserve `innerHTML` for static markup only, or (b) add a one-time `escapeHtml()` call at every `innerHTML` site where demo data is concatenated. Add a CI lint that grep-fails on `innerHTML\s*\+=` and `innerHTML\s*=\s*['"\`].*\+` in the v2 file.

### B-7. P3 — Netlify deploy has no Subresource Integrity (SRI) on `flutter_bootstrap.js`
- **Location:** `web/index.html:115` — `<script src="flutter_bootstrap.js" async></script>` with no `integrity=` attribute; `web/manifest.json` is fine.
- **Issue:** The boot script is the first thing the web app loads. Netlify serves it with the `Cache-Control: no-cache, no-store, must-revalidate` header (good — `netlify.toml:54-58`) but there is no SRI hash. A future CDN misconfiguration, a Netlify account compromise, or a MITM on an unencrypted edge (rare but possible on a stale Wi-Fi network) could swap the bootstrap for a malicious one. Flutter web's `flutter build web` does not emit an `integrity` attribute by default, and the `<script src=...>` in `index.html` is a static line.
- **Impact:** Web-app-wide RCE if compromised. Mitigated by the no-cache header (a swapped file would be re-validated on next load), but TLS termination issues or compromised cache could still hit.
- **Fix:** Run `flutter build web` and then a small post-build step that computes the SHA-384 of the deployed `flutter_bootstrap.js` and patches `<script src="flutter_bootstrap.js"...>` to include `integrity="sha384-..." crossorigin="anonymous"`. Save the hash in a build-time file so the value is reproducible. Same for `main.dart.js` if a `<script src=...>` tag is added (it currently isn't — Flutter inlines the boot).

## Agent F — Auth / session / lock

### F-1. P1 — Web idle-timer can be kept alive by any script in the origin (XSS keeps `localStorage` session "live" indefinitely)
- **Location:** `lib/main.dart:309-315` (`Listener(onPointerDown: ...)` calling `refreshWebSession()`), `lib/core/auth/web_session_web.dart:19-22` (writes `DateTime.now()` to `localStorage` on every call), `lib/main.dart:216-225` (`isWebSessionExpired` only checked on `AppLifecycleState.resumed`).
- **Issue:** The 60-minute web idle guard is meant to auto-sign-out an unattended browser tab. The reset path is a `Listener(behavior: HitTestBehavior.translucent, onPointerDown: refreshWebSession)` wrapped around the entire app body. `Listener.onPointerDown` fires for **any** pointer event the renderer sees — including those synthesized by `element.dispatchEvent(new PointerEvent('pointerdown'))` from a same-origin script. Combined with the fact that `flutter_secure_storage`'s `flutter_secure_storage_web` plugin is **plain `localStorage` under the hood** (confirmed by the package's `flutter_secure_storage_web` impl; the Flutter web `secure_storage` channel writes the session value to `localStorage` without any encryption — see `secure_session_store.dart:14-19` which still wraps it in `FlutterSecureStorage`), the practical risk chain is: any future XSS / supply-chain injection in any dependency (Syncfusion, sentry_flutter's transport, any future npm-style asset) can fire `pointerdown` once per minute and keep the session "active" forever, AND the underlying Supabase refresh token / session JSON sits unencrypted in `localStorage` for the XSS to grab. The `isWebSessionExpired` is the only enforcement, and it can be subverted.
- **Impact:** A user who walks away from a logged-in browser tab will not be auto-signed-out if any malicious script on the page runs. Even without XSS, the design relies on the *exact same* event the attacker controls to enforce the policy. Defeats the entire purpose of the web idle guard. Combined with `B-1` (open redirect to attacker-controlled APK) and the broad `'unsafe-eval'` CSP (B-4), this is a one-stop session-perpetuation primitive for an attacker who lands a payload in the page.
- **Fix:** (a) Move the idle-reset trigger from a passive DOM listener to the **Flutter route-change hook** or a real user-action filter (e.g. count only keyboard / mouse-button events, or use a debounced `Timer` that's only reset on `onAuthStateChange` / `context.push` / explicit user clicks — not on every pointer event including hover-related synthetic events). (b) Replace the `flutter_secure_storage` usage on web with `window.sessionStorage` for the Supabase session/refresh-token (scope-bound to tab, XSS-readable only for that tab's lifetime), or encrypt the value with a key derived from a server-issued CSPRNG that the client never persists. (c) Add a hard cap: even if `refreshWebSession` is called, force a re-auth after N hours regardless of activity, by reading the access token's `exp` claim from `currentSession.expiresAt` and refusing to refresh past it.

### F-2. P2 — PIN hash is a 4–6 digit code protected by 100k SHA-256 iterations (not a memory-hard KDF; PIN space is too small)
- **Location:** `lib/core/auth/app_lock_service.dart:71,251-262` (`_pinIterations = 100000`, `_hashPin` does `sha256(salt + pin)` iterated), `lib/core/repositories/user_settings_repository.dart:13,186-197` (same scheme on the server side), `lib/core/auth/app_lock_service.dart:65-69` (key names `arl.lock.pin_hash`, `pin_salt`, `pin_iterations`).
- **Issue:** A 4-digit PIN has only 10,000 possible values, a 6-digit one has 1,000,000. SHA-256 is a fast, GPU-friendly hash — 100k iterations on a single 4–6 byte input is well under 10 ms per guess on commodity hardware and is trivially parallelizable on a GPU (≈ 10⁸ guesses/sec on a single RTX 3090 against a known salt). Once the attacker has the `arl.lock.pin_hash` and `arl.lock.pin_salt` (e.g. via a rooted Android device, an iOS backup with a paired keychain, a JS console on a debug build, or a stolen device with USB debugging enabled), the PIN can be brute-forced in milliseconds. The "lockout after 3 wrong attempts" in `lock_screen.dart:166-180` is purely a *client-side* throttle — it does not affect an offline attacker iterating the hash directly. The same hash + same iteration count are also stored server-side in `user_settings.app_pin_hash` (readable via the `user_settings` SELECT RLS to the same user; not exposed to other users but never the less a stolen copy of the DB plus a stolen salt is enough to mount the offline attack against the server record too).
- **Impact:** Local PIN gate is theatre against an offline attacker with the secure-storage blob. The server-side `app_pin_hash` is also weak for the same reason. The biometric toggle (which uses the OS sensor, not the hash) is unaffected.
- **Fix:** Switch `_hashPin` to a memory-hard KDF: `package:cryptography`'s Pbkdf2 (≥ 600,000 iterations per OWASP 2023) or `package:argon2_ffi` / `package:pointycastle` Argon2id (m=64MB, t=3, p=1). Increase the minimum PIN length to 6 (currently allows 4). Store only a hash + the parameters used. Add a per-user `failed_attempts` column on the server side and an exponential backoff that requires server-side re-verification (not just a client timer) so a stolen device can't be brute-forced offline.

### F-3. P2 — `biometricOnly: false` lets the OS fall back to device passcode, defeating the "biometric" guarantee
- **Location:** `lib/core/auth/app_lock_service.dart:208-211` and `lib/core/auth/biometric_guard.dart:25-28` — both pass `AuthenticationOptions(biometricOnly: false, stickyAuth: true)`.
- **Issue:** The comment at `app_lock_service.dart:193-202` says passcode fallback is "deliberate" so a "partial sensor reading" doesn't force PIN entry. The trade-off is significant: any attacker who knows the device's lock-screen PIN/passcode (a shoulder-surfed 4-digit number, a child's remembered pattern, a recovered device with the passcode set by a family member) can satisfy the `local_auth` prompt without ever touching the biometric sensor. The app then treats the session as "unlocked" and exposes portfolio data, KYC, bank details. On Android, `setBiometricOnly(false)` also enables the `BIOMETRIC_STRONG | BIOMETRIC_WEAK | DEVICE_CREDENTIAL` auth-bound-cipher path; the app currently doesn't bind the unlocked state to a cryptographic key (no `CryptoObject` / `setUserAuthenticationParameters` use), so it's purely a yes/no gate.
- **Impact:** Weaker than expected biometric guarantee. A user who thinks "biometric = fingerprint required" can be unlocked by anyone with the device passcode. The risk is bounded by physical access to the device, but it's a deliberate weakening that should at least be opt-in or strongly surfaced in the SecurityScreen copy.
- **Fix:** Either (a) flip to `biometricOnly: true` and make the PIN-entry path the only fallback (which is what `lock_screen.dart:341-385` already supports), or (b) keep the OS fallback but require the PIN entry in the same `AppLockService.authenticate` call as a second factor when passcode is used (e.g. `authenticate` returns `authMethod: passcode` and the app then forces the user through the in-app PIN flow regardless of the OS result).

### F-4. P3 — `scrubPii` does not redact `SentryEvent.user`; signed-in user UUID ships to Sentry unscrubbed, no test covers it
- **Location:** `lib/main.dart:172-181` sets `SentryUser(id: event.session!.user.id)` on sign-in, `lib/core/observability/sentry_config.dart:100-136` (`scrubPii` mutates `event.message`, `event.exceptions[*].value`, `event.breadcrumbs[*].message`/`.data` — never `event.user`), `test/sentry_scrub_test.dart:1-105` (tests `scrubText` only, no `SentryEvent` fixture).
- **Issue:** The `SentryUser.id` set on sign-in is the Supabase auth UUID — not PII in the strict sense (it's a UUID, not an email or name), but the EU Sentry project will correlate the user's id across all events from that install and combine it with any breadcrumb / message data that slips past `scrubPii` (the `_patterns` list has no rule for `investors.id`, no rule for `user_id` columns, no rule for the `current_investor` payload). Worse: there is **no test** asserting that `scrubPii(SentryEvent(user: SentryUser(id: 'abc')))` redacts the id — the existing tests at `test/sentry_scrub_test.dart:1-105` only cover the string rules. A future "improve scrub" PR could regress the user field and CI would not catch it.
- **Impact:** Minimal direct (UUID isn't PII), but it's a gap in the documented "no PII" posture, and the test coverage leaves the user-field path silently under-tested.
- **Fix:** In `scrubPii`, set `event.user = null` (or `SentryUser(id: null)`) when `sendDefaultPii` is false — the user-id grouping is only useful if you're also collecting other user-scoped data, which the app explicitly is not. If the UUID is needed for crash de-dup, set it via `scope.setTag('user_segment', ...)` instead of `scope.setUser(...)`. Add a test: `test('scrubPii strips SentryUser', () { final ev = SentryEvent(user: SentryUser(id: 'u-1')); final out = await scrubPii(ev, Hint()); expect(out?.user?.id, isNull); });`.

### F-5. P3 — `signInWithRefreshToken` is dead code; the biometric-resume flow described in the comment never fires
- **Location:** `lib/core/auth/session_manager.dart:97-100` defines `signInWithRefreshToken`, `lib/core/auth/secure_session_store.dart:13,21,28-34,46-49` write the refresh token on every `signedIn` / `tokenRefreshed` event (`auth_provider.dart:56-79`) and provide a `readRefreshToken()` reader, but **no UI screen ever calls `signInWithRefreshToken` or `readRefreshToken()`** — `search_files` for `signInWithRefreshToken|readRefreshToken` matches only the definition lines. `auth_provider.dart:24-37` seeds the stream from `client.auth.currentSession`, not from the cached token.
- **Issue:** The `BiometricScreen` and `LockScreen` both call `local_auth` / `verifyPin` to "unlock" the app, but the **app session itself** is already live in the in-memory `supabase_flutter` client — there's nothing to re-authenticate. The biometric prompt is a UI gate over a session that was never lost. The whole `SecureSessionStore.saveSession` / `setBiometricEnabled` / `clearBiometric` infrastructure is therefore write-only: the refresh token is being persisted to `flutter_secure_storage` on every sign-in and token refresh (i.e. continuously while the user is signed in), accumulating PII at rest, but never consumed. This is misleading documentation (the comment at `session_manager.dart:92-96` describes a biometric-resume path that does not exist) and an unnecessary attack surface (a future maintainer who reads the comment will think the refresh token is the biometric-resume key, and may rely on it being valid longer than the actual Supabase server-side TTL).
- **Impact:** Hygiene + unnecessary data-at-rest (Supabase refresh token persisted for the lifetime of the session, with no consumer). No direct exploit, but a future code change that calls `signInWithRefreshToken` from a screen that "unlocks" the app will then rely on the assumption that the cached token is still valid; the in-memory client has already been refreshing it in parallel, so the user will end up with two concurrent sessions and the "old" token will fail server-side and the user will be silently signed out.
- **Fix:** Either (a) wire the biometric-resume flow end-to-end (after successful `authenticateBiometric`, look up the cached refresh token via `secureStore.readRefreshToken()`, call `SessionManager.signInWithRefreshToken(token)`, and invalidate the in-memory `client.auth.signOut()` from the previous session), or (b) remove `SecureSessionStore.saveSession`, `readRefreshToken`, `signInWithRefreshToken`, and the `signedIn/tokenRefreshed` write loop in `auth_provider.dart:56-79` — the in-memory session is the only session that matters, and the secure-store write is dead code.

### F-6. P3 — OTP screen has no client-side attempt counter; the 60s resend throttle is the only UI guard
- **Location:** `lib/features/auth/otp_screen.dart:106-148` (`_verify` shows `Wrong code, try again` and clears the boxes; no `_wrongAttempts` counter, no cooldown, no escalating backoff), `lib/features/auth/otp_screen.dart:184-215` (resend cooldown is 60s).
- **Issue:** Supabase Auth's default `verifyOTP` will accept 6-digit codes with a default expiry of 1 hour and will rate-limit at the gateway, but the **client** will keep firing `verifyOTP` requests indefinitely with no throttling. A user (or an attacker who has hijacked the session after the email was delivered, e.g. a shared inbox) can hammer the verify endpoint. The `LockScreen` enforces a 3-strike 30-second cooldown (line 166-180) but the OTP screen does not. There's also no "max attempts → require re-send" path: the user can keep entering wrong codes for the same 1-hour OTP window.
- **Impact:** Limited by Supabase's server-side rate limit, but a non-trivial script that knows the email and the right time window can iterate 6-digit codes server-side at a meaningful rate. The 6-digit space (10⁶) is large enough that it's not trivially brute-forced within 1 hour at any realistic rate limit, but a 4-digit code (if Supabase is ever reconfigured for `otp_length=4` — see `request-auth-email/index.ts:135-142` which doesn't pin the length) is 10⁴ and well within reach. The plan file in `docs/plans/2026-04-27-production-readiness-plan.md` doesn't document the current Supabase OTP length setting.
- **Fix:** Add a client-side counter: after N (3) wrong `verifyOTP` responses, switch the screen to a "resend required" state that hides the boxes until a new code is requested. Document the Supabase project's `OTP_LENGTH` and `OTP_EXPIRY` settings in a comments block in `request-auth-email/index.ts` so future config changes don't silently downgrade the security posture. Consider also adding a per-IP and per-email rate limit inside the edge function itself (`Map<email, { count, windowStart }>` with a 60-second window — Supabase Auth's gateway does this, but the function would surface cleaner 429s and protect against misconfigured gateway settings).

### F-7. P3 — `ARL_AUTH_GATE_SECRET` is bundled in `.env` and shipped in the release APK / web build
- **Location:** `lib/core/constants/supabase_constants.dart:88-91` (`authGateSecret` reads from `--dart-define` or `.env`), `lib/core/auth/session_manager.dart:56,62-67` (sent as `x-arl-cron-secret` header), `.env` line 1-3 (file present in repo, bundled as `flutter_assets/.env` per B-2).
- **Issue:** The auth-gate secret is the *only* authentication on the `request-auth-email` edge function (no JWT, no signed-URL, no Supabase user context — the function runs with service role). Anyone who can extract the secret from the APK (B-2 already documents the 5-second `unzip` extraction) can call `request-auth-email` for any email at will. The function's only protection against enumeration is that it returns the same generic reply for unknown vs. known emails (so brute-forcing "is email X a registered investor" via timing is also defused by the function's `await fetch(... auth/v1/otp ...)` being skipped for unknowns), so the secret leak is *not* a full enumeration vector — but it does allow **email bombing**: anyone can spam the "6-digit code" email to every registered investor, causing inbox flooding and ad-hoc phishing confusion. The function's per-investor OTP dispatch (line 134-155) doesn't have a per-investor rate limit.
- **Impact:** Email spam at any registered-investor's expense, at attacker-controlled cadence. Not a credential or data leak, but a real user-experience / trust attack.
- **Fix:** (a) Move the secret from `.env` (which B-2 already shows gets bundled) to `--dart-define` only and remove the `dotenv` fallback for this key. (b) Add a per-investor cooldown in `request-auth-email/index.ts`: store `last_otp_sent_at` in a `private.otp_request_log` table (or a KV) and refuse to dispatch if a new code was sent within the last 60 seconds, regardless of the secret check. (c) Consider verifying a Supabase-issued JWT in the function (the calling app always has one — `client.functions.invoke` attaches the anon JWT by default), so the function rejects anonymous calls entirely.

### F-8. P3 — `flutter_secure_storage` on web stores the session material in plain `localStorage` (the "secure" prefix is misleading)
- **Location:** `lib/core/auth/secure_session_store.dart:14-19` (`FlutterSecureStorage(aOptions: AndroidOptions(encryptedSharedPreferences: true))` — no `webOptions` provided), `pubspec.lock:329-340` (confirms `flutter_secure_storage_web` is pulled), `lib/core/auth/web_session_web.dart:9-16` (a separate plain-localStorage key for the idle timestamp, but the actual session JSON goes through `flutter_secure_storage`).
- **Issue:** On Android and iOS, `flutter_secure_storage` is genuinely backed by the Keystore / Keychain. On web, the `flutter_secure_storage_web` package writes to `localStorage` in plaintext. The session/refresh-token / last-email values are therefore readable by **any** same-origin script. The plugin does provide a `WebOptions(dbName: ..., publicKey: '...')` for AES-GCM wrapping, but `secure_session_store.dart` does not configure it (no `WebOptions` arg in the `FlutterSecureStorage(...)` constructor at line 16-18). Combined with F-1, any XSS that lands in the web build's origin can read the Supabase refresh token from localStorage and call `setSession` from any other browser tab / device to hijack the account.
- **Impact:** The "secure" branding of the local session store is wrong on web. The Supabase refresh token sits in plaintext localStorage.
- **Fix:** Add `WebOptions(dbName: 'arl_secure_session', publicKey: 'arl_web_v1_...')` to the `FlutterSecureStorage(...)` constructor in `secure_session_store.dart:16-18`. The public key only obfuscates (it's in the source), so this is **not** a real defense — a determined attacker who can read the JS bundle can decrypt — but it raises the bar above "trivial grep for `arl.auth.refresh_token` in `localStorage`". The right long-term fix is to move the Supabase session to `sessionStorage` (tab-scoped, not exposed to other tabs of the same origin) and refresh it via a server-issued HttpOnly cookie that only the Supabase JS client knows how to consume.

### E-1. P0 — bank-change-request: no IFSC / holder-name validation and no identity re-verification gate
- **Location:** `supabase/functions/bank-change-request/index.ts:114-132` (parsing), `:160-170` (insert), `:189-200` (email)
- **Issue:** The function performs only ONE input validation: `account_masked` must match `/^X+(-X+)*-\d{4}$/`. The `ifsc`, `holder_name`, and `bank_name` fields are accepted as any non-empty string of any length and any character set. There is no RBI IFSC regex (must be `/^[A-Z]{4}0[A-Z0-9]{6}$/`, 11 chars). There is no length cap on `holder_name` (a 10 MB string is stored). There is no `kyc_status='verified'` precondition — an investor whose KYC is `pending` or `rejected` can still change their payout bank account. - **Impact:** (1) Trivial DoS: a 10 MB `holder_name` is stored in `bank_change_requests.new_holder_name` and re-rendered into every subsequent ops email — a self-inflicted email-bombing surface. (2) Phishing: ops cannot trust the holder_name field to be the real account holder. (3) Account takeover: a session-token thief (cookie theft on a kiosk, a leaked JWT) submits a bank change and ops approves it because the request looks like the real investor.

### E-2. P1 — bank-change-request: ops email body trusts all four un-validated inputs

- **Fix:** Make `documents` UNIQUE on (investor_id, zoho_file_id) — already covered by the storage path being `investor/${inv.id}/${att.id}.${ext}`. Confirm the DB-level constraint matches the storage-path assumption. Add a `ignoreDuplicates: false` log-and-continue on 23505 in PART B too, so the run report reflects the failure.

### E-8. P2 — six cron functions share one CRON_SECRET; one leak compromises all
- **Location:** `supabase/functions/{gallery-sync,documents-sync,zoho-reconcile-daily,health-check,sync-stale-alert,notify-consultation-request}/index.ts` (all read `Deno.env.get("CRON_SECRET")` and match against the same `x-arl-cron-secret` header)
- **Issue:** All six functions use the same env var `CRON_SECRET` and the same request header `x-arl-cron-secret`. Migration 016 explicitly says "reuse the same secret"; migration 056 also says "reuse the gallery-sync value". The functions are deployed independently and could be invoked by any caller that has the secret. `documents-sync` writes to BOTH `arl-documents` storage AND the `documents` and `project_documents` DB tables — and `notify-consultation-request` posts to Slack (where the message includes the investor's email + phone). A compromise of the secret affects: photo pipeline, document pipeline, CRM reconcile, health dashboard, stale-alert monitoring, and consultation-request Slack posts.
- **Impact:** Single point of compromise. If the CRON_SECRET leaks (e.g. logged in CI, stored in a developer's shell history, scraped from a public Sentry breadcrumb), an attacker can: (a) trigger a storage-bombing by repeatedly calling documents-sync with a body of `{}` (each call hits Zoho for every LLP + every investor), (b) drain the Zoho API token's rate limit, (c) inject Slack messages to ARL ops impersonating a real consultation request.
- **Fix:** Split into per-function secrets: `CRON_SECRET_GALLERY`, `CRON_SECRET_DOCS`, `CRON_SECRET_RECONCILE`, `CRON_SECRET_HEALTH`, `CRON_SECRET_ALERT`, `CRON_SECRET_CONSULT`. The migration 016 + 056 reuse is convenient but not safe. At minimum, rotate the secret on a 90-day cadence and log every invocation to `webhook_log` so leaks surface in audit.

### E-9. P2 — sync-stale-alert: no alert de-duplication; every hourly run inserts a fresh row
- **Location:** `supabase/functions/sync-stale-alert/index.ts:83-99`
- **Issue:** When a table is stale, the function inserts ONE `sync_alerts` row per (table_name, run). Over a 6-hour CRM outage on `investor_units` (threshold 2h), the alert table accumulates ~3 rows. Over a 24-hour outage on `llps` (threshold 24h), the FIRST stale hourly run inserts an alert; subsequent runs find `llps` still stale and insert another alert. There is no UNIQUE constraint or "last alert for this table" lookup, and the `health-check` consumer simply counts alerts. Ops sees a flood of duplicates for one incident and risks alert-fatigue.
- **Impact:** Alert fatigue; ops may dismiss a real second-incident alert as a duplicate of the first. Not security, but it weakens the only monitoring signal the team has.
- **Fix:** Add a UNIQUE on (table_name, alert_window_start) where alert_window_start is bucketed to the threshold (e.g. floor(now() to hour for the 2h bucket). Or use an UPSERT with `onConflict: "table_name,threshold_secs"` and `ignoreDuplicates: false` to update the `last_alerted_at` instead of inserting. Better: insert ONE alert per (table, threshold) when it transitions from fresh to stale, and a separate "resolved" row when it transitions back.

### E-10. P2 — bank-change-request: holder_name not length-bounded → email-bombing + DB bloat
- **Location:** `supabase/functions/bank-change-request/index.ts:114-122`
- **Issue:** The function requires `holder_name` to be present and non-empty but does not check length. A malicious or buggy client can submit a 10 MB `holder_name`. It is stored in `bank_change_requests.new_holder_name` (TEXT, no length cap) AND re-rendered into the HTML email body on line 197. Every subsequent page-load of the bank-change history (an investor's own list, the ops list) will fetch this row and render it. Self-inflicted DoS.
- **Impact:** DoS via a single authenticated call. The function is rate-limited at 7 days per investor, so the attack requires 7 days per request — but with 50-500 investors in the system, the surface is non-trivial.
- **Fix:** Add `.length > 100` check returning 400. Same for `bank_name` (cap at 80) and `ifsc` (cap at 11 — strict).

### E-11. P2 — bank-change-request: no `kyc_status` precondition
- **Location:** `supabase/functions/bank-change-request/index.ts:160-180`
- **Issue:** The function looks up the investor's name and ARL ID (line 183-187) but does NOT check `kyc_status`. An investor with `kyc_status='pending'` or `'rejected'` can submit a bank change. The risk surface: the ops team will receive a bank-change request from an investor who hasn't even been KYC-verified. There is no business reason to allow a bank change before KYC is complete.
- **Impact:** Ops time wasted on bank-change requests from un-verified investors. Lower bar for an attacker to plant a takeover pivot.
- **Fix:** Read `kyc_status` in the same investor lookup (line 183) and return 400 with `error: "kyc_required"` if not `verified`.

### E-12. P3 — consultation_requests_repository.dart uses `client.auth.currentUser!.id` (non-null assert) instead of `ArlSupabase.currentUserId`
- **Location:** `lib/core/repositories/consultation_requests_repository.dart:18, 88`
- **Issue:** Line 18 does `final uid = client.auth.currentUser!.id;` which throws if `currentUser` is null mid-restore. Line 42-50 also uses `uid` as the value of `user_id` for the INSERT — this is the defense-in-depth echo that the project's coding style guide says to AVOID (per the `investor_repository.dart` comment: "We rely on RLS for filtering rather than echoing currentUserId back as a .eq clause"). It's not a security bug because RLS is `user_id = (SELECT auth.uid())` and the JWT carries the truth, but it does mean a race can throw a `StateError` to the UI.
- **Impact:** Crash on the Explore screen's "Request Consultation" button if tapped in the 100-200 ms window between session-restore and `currentUser` being populated. Functional, not security.
- **Fix:** Switch to `final uid = ArlSupabase.currentUserId; if (uid == null) throw StateError('not signed in')` and add a session-wait like `investor_repository.dart:40-44`. The bigger smell: the Dart-side `uid` echo is redundant with RLS and adds a footgun.

### E-13. P3 — privacy_repository.dart: `erasure_requests` and `nominees` RLS not verified
- **Location:** `lib/core/repositories/privacy_repository.dart:74-115` + the underlying tables (no RLS migration found for `erasure_requests` or `nominees` in `migrations_archive_20260608/`)
- **Issue:** The privacy export reads from `nominees`, `erasure_requests`, `consents` and writes to `nominees` (upsert/delete) and `erasure_requests` (insert). The SELECT statements include `.eq('investor_id', uid)` and `.eq('user_id', uid)` — defense-in-depth. But there's no migration in this audit's scan range that creates RLS on these tables. The default `019_revoke_default_grants.sql` revokes anon and grants SELECT to authenticated, which means **without an RLS policy, authenticated users can read all rows**. The Dart-side `.eq()` filter limits reads to the caller's own row in the app, but a hand-crafted PostgREST GET (e.g. from a curl after sign-in) would return every nominee + every erasure request.
- **Impact:** PII leak surface: any authenticated investor can read every other investor's nominee + erasure request via direct PostgREST. The Dart app's `.eq()` masks this for normal users, but it's a defense-in-depth gap.
- **Fix:** Add a migration like migration 028/029 did for `consultation_requests` and `exit_requests`: enable RLS on `nominees`, `erasure_requests`, `consents` and add the standard `TO authenticated USING (investor_id = (SELECT auth.uid()))` policies. Migration 059 (privacy rights) may have done this — verify in 059.

### E-14. P3 — projects_repository.dart: myProjects in-memory `ids.toSet()` then `inFilter` — RLS handles it but a noisy query
- **Location:** `lib/core/repositories/projects_repository.dart:54-74`
- **Issue:** The function does `client.from('investor_units').select('project_id')` (no filter — RLS does it) → builds a Set of project_ids in Dart → does a second `.from('projects').select().inFilter('id', ids).isFilter('deleted_at', null)`. The RLS on `projects` already filters to (marketplace OR own-units) AND `deleted_at IS NULL`. The Dart-side `.inFilter` is redundant AND the `.isFilter('deleted_at', null)` is redundant. Not security (defense-in-depth, fine), but the design pattern diverges from the project's stated convention ("rely on RLS, not Dart-side echo") in `investor_repository.dart:18-20`.
- **Impact:** None security-wise. The double filter is harmless because RLS returns 0 rows for other-investors' projects. The code-smell is that one repo says "rely on RLS" and another doesn't.
- **Fix:** Drop the `.inFilter('id', ids)` and rely on the RLS predicate `id IN (SELECT project_id FROM investor_units WHERE investor_id = auth.uid())` plus `is_listed_in_marketplace = true`. The `inFilter` here is silent IDOR defense-in-depth, so leaving it is also fine.

### E-16. P3 — sync_status SECURITY INVOKER + count leak: when called by an authenticated user, counts/MAX are per-user, not global
- **Location:** `supabase/migration_archive_20260608/20260513000100_035_sync_status_security_invoker.sql:26` + the view definition (referenced in mig 023, not read in this audit)
- **Issue:** Migration 035 flipped `sync_status` to `security_invoker = on`. The view aggregates `COUNT(*)` and `MAX(last_synced_at)` across `llps`/`projects`/`investors`/`investor_units`. With INVOKER, an authenticated caller sees per-RLS-visibility counts — which means an investor calling this view sees only their own row count for `investors` (1) and the count of LLPs visible to them (0 — no LLP RLS exposure for non-platform users). The current consumers are all `service_role` (which bypasses RLS), so practical behaviour is unchanged. BUT: if a future contributor exposes the view to investors (e.g. a "platform stats" screen), the counts will silently misrepresent platform-wide totals.
- **Impact:** Future contributor footgun. Not a current bug.
- **Fix:** Either (a) keep `security_invoker = off` on `sync_status` (revert mig 035) and document "service_role only" in the view COMMENT, or (b) create a separate `sync_status_global` view with `security_invoker = off` for the service_role consumers and keep `sync_status` as the user-scoped one. Current setup is the worst of both: it has the footgun (INVOKER) but the COMMENT says "service_role only" — contributors will read the COMMENT, not the reloptions.

### E-17. P3 — exit_requests: the Dart repo writes `user_id` (auth.uid) but the DB stores it; no investor_units FK to user
